01设计演进

v0.3 不推翻前两版，而是把它们收进同一套内核。

版本解决的问题留下的问题
v0.1四层架构、握手、能力路由、会话透传、Agent 池断线补推、重启恢复、治理不足
v0.2link epoch、outbox/ack/resume、peer 策略、防环、背压会话/事件仍是单节点视角，无法内嵌
v0.3可嵌入 Core、AgentProfile、统一 Session/Turn/Event、Channel、统一调度改造成本大，需分阶段迁移

02目标与原则

一个 Core

独立节点与宿主内嵌共用；HTTP/Web/Peer 监听由宿主决定。

一个会话模型

Feishu / Web / Peer / API 都是 Session(channel)。

一个事件契约

seq + turnId；适配器只负责渲染与重放。

一个调度面

全局 → Profile → Session 串行；租户配额与优先级。

一个协议

Peer 协议只在连接层实现，不再有桥接翻译层。

轻量

单进程 + SQLite，不引入 MQ/注册中心。

非目标：多跳 relay、并行 fan-out、动态发现、跨节点强一致事务。

对外端口默认仅 8788：Web / HTTP / WS / /peer 复用
内网后端opencode 4097/4096 不等同于 X 端口，不对外暴露
状态所有权SQLite 是单实例唯一事实源；peer 不共享数据库
执行所有权opencode 拥有 LLM 上下文；X 持久化 agentSessionId 与消息

flowchart TB A[启动] --> B[加载 sessions / turns] B --> C{存在未完成 turn?} C -->|否| Z[完成] C -->|是| D{channel = peer?} D -->|是| E[resume 握手] E --> F{对端可恢复?} F -->|是| G[补推并恢复] F -->|否| H[按策略重开/失败] D -->|否| I{agentSessionId 仍有效?} I -->|是| J[恢复执行] I -->|否| K[用历史消息重放或标 interrupted] G --> L[重发 pending_interactions] J --> L K --> L
场景行为
peer 断线outbox 保留，resume 后补推，旧 epoch 丢弃
peer / X 重启resume 或按 openId/promptId 重开；终态唯一
本地 agentSession 失效历史消息重放上下文，标注已重建
Feishu/Web 重连按 seq 重放或拉取历史；pending 交互重发
取消与 done 竞态先到终态生效，迟到事件审计不重复展示

10安全与治理

  • Channel：Feishu 用户/群白名单、命令权限；API/Web Token。
  • Peer：公钥固定、allowlist、requireWss、并发/速率/TTL、能力白名单。
  • Profile：readOnly、允许的 channel/peer 范围。
  • 绑定：Web/Admin 仅 127.0.0.1；peer 端口按需公网。
  • 审计：traceId + channel + externalRef + peerId。

12可观测与管理

Peer

state、reconnect、RTT、stale epoch、outbox 积压、错误码。

Session

按 channel/profile/peer 的活跃数、队列、等待时长。

Event

chunk 延迟、订阅者 lag、重放次数、背压触发。

资源

opencode 健康、profile 租约、全局并发。

管理台：会话按 channel/peer/profile 过滤；peer 详情、drain、密钥轮换；Feishu 配置与 profile 切换。
