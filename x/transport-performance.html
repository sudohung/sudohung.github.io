01目标与问题

先减少消息/DB 写入次数，再压缩单条大小，最后用压缩/二进制进一步节省带宽。

当前单 chunk

信封 409–419 B，ack 362 B；单次往返约 780 B。

SQLite ack

seq <= ? 累积更新 O(n²) + FULL sync；2000 条约 6.5s。

接收端

每 chunk 一次 inbound_seq 查询 + upsert。

目标

消息/DB 写入下降 10x+；ack ≥10k/s；1KB 级协议开销 ≤20%。

03Chunk 聚合

图 2：100ms / 64KB / 控制事件前 flush

flowchart LR A[text / reasoning 事件] --> B[ChunkAggregator
按 session+turn] B --> C{100ms 到?} B --> D{64KB 到?} B --> E{控制事件?} C -->|是| F[flush batch] D -->|是| F E -->|是| F F --> G[分配 turn 内 seq] G --> H[chunk.batch → OutboxBuffer → PeerLink] E -->|question/permission/done/error| I[先 flush 文本 batch] I --> J[发送控制事件]
  • 一个 batch 一个 seq、一个 ack、一行 outbox。
  • 控制事件与 batch 共享 turn 内单调 seq，保证顺序。
  • 对端不支持 batch 时回退逐 chunk。

05Ack 水位

图 4：累计确认、outbox 清理与 inbound 去重

sequenceDiagram participant B as Executor B participant A as Receiver A participant W as Worker B B->>A: chunk.batch(seq=n) A->>A: inbound 水位 = n（内存） A-->>B: chunk_ack(n / watermark) B->>B: ack 水位 = max(current, n) W->>W: 每 500ms 批量 upsert 水位 W->>W: 每 30s 删除 acked 旧行
  • WebSocket 有序；ack 水位可累计确认，不再逐行 seq <= ?。
  • 检测到 seq 缺口时暂不推进水位，等待补齐/重放。
  • chunk 崩溃窗口内可能重复展示；final 消息按 turn 幂等。

08配置与语义

"transport": {
  "chunkBatch": { "flushIntervalMs": 100, "maxBytes": 65536 },
  "persistence": {
    "workerTickMs": 500,
    "flushEveryTicks": 1,
    "criticalFlush": true,
    "synchronous": "NORMAL",
    "ackedCleanupEveryTicks": 60,
    "ackedRetentionMs": 3600000,
    "cleanupLimit": 5000,
    "walCheckpointEveryTicks": 60
  },
  "compression": { "perMessageDeflate": true, "threshold": 1024, "level": 6 },
  "msgpack": { "enabled": true }
}
崩溃语义：未 flush 的 chunk 最多丢一个 tick（turn 中断）；done/error 发送前已 flush；ack/inbound 水位回退可能造成重发/重复展示，但最终消息按 turn 幂等。
